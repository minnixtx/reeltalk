### Stack audit (executed 2026-09-05, commit `95b332c`)

Per AUDIT-BRIEF.md (consumed + deleted in that commit): audited the M0 stack against current best practice and applied changes in-repo. Full findings table + rejected alternatives: PLAN.md §3.9; license verdicts for new/changed deps: PLAN.md §4.4.

**What changed (applied):**

- **Redis removed** entirely: LocMemCache + DB sessions.
- **nginx removed**: whitenoise serves static in-process; media via a `serve` URL pattern; web exposes :3030 directly (D14 operator TLS unchanged).
- **Dockerfile**: lockfile-first layer caching, venv at /app/.venv, **non-root `appuser`**.

- Generate migrations locally (no rebuild): `docker run --rm -v /home/minnix/reeltalk:/src:z -w /src --entrypoint /app/.venv/bin/python reeltalk-web manage.py makemigrations <app>` (the `failed to resolve host 'db'` warning is harmless — makemigrations doesn't need the DB).

- Then `docker compose build web` and `docker compose run --rm web bash -c 'ruff check . && ruff format --check . && pytest'`.
- If a test-DB migration fails mid-run, a stale `test_reeltalk` DB is left behind: drop it with `docker compose exec -T db psql -U reeltalk -d postgres -c 'DROP DATABASE IF EXISTS test_reeltalk;'` before re-running.

### M1 increment 3 — Shelf/ShelfFilm + binary defaults + merge/absorb (executed 2026-09-06, commits `d45a1e4`, `cac1627`)

Third increment of M1. `Shelf` + `ShelfFilm` models in `reeltalk.core` (R9), the D1 binary default shelves created on user save, and the full merge/absorb logic (§3.2). No new runtime deps.

**What landed:**

No privacy/editable fields in v0.1 — the custom-shelf UI is gone (D16); M4's wire type can add what it needs then.
- `ShelfFilm` (through row): shelf (CASCADE) / film (**PROTECT** — a film cannot be deleted while shelved; merge re-points first, so merges are unaffected) / user (the actor who shelved; non-null, defaults to the shelf owner in save()) / shelved_date; unique (film, shelf). Django 6.1 gotcha: the M2M manager's `.add()` bulk-inserts **without calling the through model's save()**, so shelving code creates rows explicitly or passes `through_defaults={"user": ...}` — documented on the model (R14).
- Default shelves on user save (R15): a new **local** user gets both D1 shelves via `User.save()` → `Shelf.create_default_shelves`; remote mirrors (M4) receive their shelves from federation instead. Import direction is social→core only; core references `"social.User"` as a string FK, so no Python or migration cycle (core/0003 depends on social/0001 via `swappable_dependency`).
- Merge/absorb (R16): `Film.merge_into(canonical)` — all-or-nothing (`transaction.atomic`): backfill empty fields onto the canonical via an explicit field list (subtitle/description/year/runtime/poster/tmdb_id/imdb_id scalars; order-preserving union for the genres/directors/cast arrays), re-point ShelfFilm rows (shelved_date + actor preserved; a film already on the same shelf absorbs its duplicate row) and `User.blocked_films`, record the MergedFilm old→new mapping, delete the absorbed row. Identity/provenance fields (title/sort_title/origin_id/remote_id/dates) are never backfilled. Status re-pointing slots in at increment 4 via `_repoint_related()` — one block per related model.
- Admin: minimal ModelAdmins for Shelf + ShelfFilm.

**Gotchas hit & fixed:**
- **Backfill vs unique constraint.** Saving the canonical *before* deleting the absorbed row made a backfilled `tmdb_id` collide with the value the absorbed row still held (`core_film_tmdb_id_key`). Order is now: re-point → MergedFilm row → delete absorbed → save canonical — all inside the transaction, so any failure rolls back wholesale.
- **`delete()` clears the instance pk.** After `merge_into`, the absorbed instance's `.id` is None (Django sets it); callers/tests must capture the id beforehand.

### M2 increment 3 — worker service (executed 2026-09-09, commit `c5c611f`)

Third increment of M2. The task queue lands per R4: **Django-Q2 on a Postgres cluster** replaces the deferred celery + django-celery-beat + redis broker in one package — no Redis service at any milestone. No model changes; the first (and only) real task is the D11 backfill wrapper.

**What landed:**

- **Settings:** `"django_q"` in INSTALLED_APPS (its ORM cluster tables) + `Q_CLUSTER`: name `reeltalk`, workers 2, timeout 3600 (explicit — a full import backfill runs ~15 min under D11 pacing), retry 7200, orm `default`, backend `postgresql` (R28).

- **Compose:** a `worker` service — same image, `command: python manage.py qcluster`, `depends_on: web: condition: service_healthy`. **Gotchas hit & fixed (all 1.11 version specifics, verified against installed source):**
- **The warning condition is `timeout > retry`, and there is no `retry_timeout` key in 1.11.** `Q_CLUSTER["retry"]` (default 60) is the acknowledgement wait for delivery-guaranteed brokers; with timeout 3600 django-q warns "Retry and timeout are misconfigured" at every startup until `retry >= timeout`. Set `retry: 7200`; an earlier attempt with a non-existent `retry_timeout` key did not silence it.
- **Model/queue shape differs from older docs:** queued work is a signed package (`SignedPackage`, Django signing + pickle) in `django_q_ormq` (`OrmQ`); a `Task` row (success/stopped/result fields — no `status` column, no `return_value`) only appears when the task executes. Tests assert on the decoded `OrmQ` payload for enqueue and the `Task` row for execution.
- **`docker compose run web ... pytest` injects `.env` via `env_file`** — so the real TMDB key is present in the test environment (the image itself stays clean; `.dockerignore` excludes it). Any test that needs the unconfigured path must force it with `override_settings(TMDB_API_KEY="")`.

The stack is left running with all three services.

### M4 increment 1 (executed 2026-09-10, commit `d77efef`)

**What landed:**

### M6 increment 1 — daily pg_dump backup job (executed 2026-09-14, commit `7e668cb`)

First increment of M6: the "daily `pg_dump` backup job" from PLAN.md §3.8/§5, which the plan requires before public deploy. **One system package added** (`postgresql-client`, license-audited in PLAN.md §4.7); no model changes, no migrations, no new Python deps.

**What landed:**
- **`backup_database` management command** (`reeltalk/core/management/commands/backup_database.py`) — the repo's first. Dumps the configured database with `pg_dump --format=custom` into `settings.BACKUP_DIR` (default `/app/backups`, the backups volume) and prunes older dumps down to `settings.BACKUP_RETENTION` (default 7). Connection params come from Django's live `connection.settings_dict`, so it targets whatever DB the app points at (the real one in prod, the test DB under pytest); the password goes through `PGPASSWORD`, never argv. Two pure helpers (`dump_filename`, `dumps_to_prune`) are directly testable without a DB or binary; filenames are zero-padded UTC timestamps so lexicographic order == chronological, which drives retention.
- **`backup` compose service** — its own long-running service (independent of web/worker health) running `backup-loop.sh`: a lean sleep loop (no cron dependency) that wakes once a day at `BACKUP_TIME` (default 03:17, container TIME_ZONE) and calls the command; a failed run logs a warning and retries next day rather than exiting. Mounts the new `backups_volume`.
- **Dockerfile** — `postgresql-client` added to the runtime image (provides `pg_dump`/`pg_restore`; §4.7); all three app-image services (web/worker/backup) share it. `/app/backups` is created appuser-owned in the image and declared a VOLUME, so the named volume initializes writable by the runtime user (the same artifact-volume ownership fix as `static_volume`/`media_volume`).
- **Settings + config** — `BACKUP_DIR` + `BACKUP_RETENTION` (env-overridable); `.env.example` documents the knobs (`BACKUP_TIME`/`BACKUP_RETENTION`/`BACKUP_DIR`) + a restore one-liner.

**Design notes (R58):** custom format (`-Fc`) over plain SQL — smaller, gzip-compressed, `pg_restore`-able, the Postgres-recommended default for automated backups. A dedicated service over a Django-Q2 scheduled task: backups must run regardless of app/queue health, and this avoids adding a qcluster `--beat` process, while the dump logic stays in one tested command (the service is just a thin daily wake). Retention is count-based (keep newest N), predictable at v0.1 scale.

### M6 artwork polish — weathered background plate (executed 2026-09-18, commit `4a79d80`)

Polish item 2: the distressed background was "a little too subtle and can be hard to notice at all" next to `MOCKUP.png`; goal stated as a more **worn and weathered** look. Recorded as **R66**.

**Measured before designing.** Sampling background-only pixels: our page background sat at **luminance 9.1 / stddev 1.9** (effectively flat) while the mockup's backgrounds sit at **lum 12–22 / stddev 15–32**. The owner-supplied tile was never the problem — it measures lum 15.2 / stddev 14.5; the `rgba(9,8,7,.86)` scrim was erasing ~86% of its grain.

**The trap worth recording:** thinning the scrim is the wrong lever on its own. Simulating the CSS stack (scrim over tile over `--black`) showed that hitting the mockup's stddev with the raw tile needs alpha ≈ .58, which drags **mean luminance to 43–56** — a muddy grey page, nothing like the reference. The mockup is **bimodal**: near-black areas plus sparse bright wear (dust, scuffs, peeled paint). Its margins carry high local contrast at a *low* mean, which only comes from bright marks on a dark base, not from lifting the whole plate.

**What landed:**
- **`reeltalk/social/static/images/grunge-weathered.png`** — derived from the owner's tile so the grain identity carries over (REWRITE.md rule 4: our own derived asset). Pipeline: autocontrast → **gamma-crush the midtones** (`x^2.7`) so the plate averages near-black → multiply a periodic low-frequency field to carve deep large-scale worn blotches → screen on **dense dust flecks, short scuffs and long streaky scratches** (the real source of the prominence) plus a handful of near-invisible pale veils. Every layer is built **periodic** (integer-frequency sinusoids over the tile width) or drawn wrapped at `x-W`/`x`/`x+W`, so it still tiles seamlessly.
- **Scrim `.86 → .62`**, now a pure prominence dial rather than a brightness one: with the plate's mean pinned low, page-background stddev rises **1.9 → 8.0** while mean luminance *drops* **9.1 → 7.5** — more visible wear, darker page, text contrast untouched. Content-column region measures stddev 29.5, inside the reference band.
- **Asset weight**: quantized FASTOCTREE 256-color → **228 KB** (from a 2 MB full-colour render; mean channel error ≈ 2/255, invisible), in keeping with the owner's earlier asset-size preference.
- The original `grunge-background.png` (2.8 MB) is now referenced nowhere but **kept** — deletion was offered and not requested, so it stays as the source tile.

**Dead ends worth remembering:** (a) lifting the plate's overall brightness raises the mean without buying variation; (b) pale "worn patches" above roughly lum ~50 read as **soft clouds/bokeh dots**, not wear — single blurred ellipses especially, so patches are built as irregular clusters and kept dim; (c) clustered saturated warm speckle reads as colour noise, so dust is neutral-warm `(v, .95v, .88v)` and evenly spread.

### M6 artwork polish — wordmark relit as red glass with a hot filament (executed 2026-09-18, commit `085c10b`)

Polish item 4, the direct follow-on to item 3: "the new nav bar selection glow looks really good, but now the main ReelTalk logo looks somewhat dim compared to it" — the owner asked for similar treatment on the wordmark. Recorded as **R68**.

**Measured before designing.** Sampling the lit pixels of the wordmark region on the live page: `.brand` was a flat `#f9a58f` fill with **max luminance 193 and zero pixels above 200** — a uniform pale salmon with no hot spots anywhere, which is why it read as paint rather than light. The mockup's wordmark in the same measurement is **bimodal**: max 250, p90 220, **22.8% of lit pixels ≥200**, 0.7% ≥240 — deep red glass carrying sparse white-hot filament highlights (R66's contrast-at-low-mean lesson again).

**What landed (CSS only, `.brand`):**
- **Fill is the filament, the stroke is the glass.** `color: #fff4ee` plus `-webkit-text-stroke: 0.0174em var(--red)` left in the default paint order, so the stroke paints *over* the fill and carves red back into each Monoton bar, leaving a narrow white-hot core — the only one of seven rendered recipes that reproduces the reference's per-stroke structure. Setting `paint-order: stroke fill` instead puts the glass under the filament and loses it (that was round 1's variant B).
- **Bloom rebuilt from four stops to six:** `0 0 2px #fff → 5/12px --red-bright → 26px --red → 48px rgba(255,40,25,.7) → 80px rgba(255,30,20,.35)`.
- **Rejected after being built and measured:** plain hot fill (max 243 but 25% of pixels near-white — reads white/pink, not red neon), gradient-clipped tube via `background-clip: text` (hot crown pooling to red, no per-stroke core), a heavier 1.6px stroke (swallows the filament: flat red, max 211), and a warm step-up of the existing salmon (brighter, still no true core).

**The mobile trap — worth keeping.** The first build used `-webkit-text-stroke: 1px`. Under 40rem the brand steps down to 2.2rem, where Monoton's bars are only ~2–3px wide, so a fixed 1px glass edge **ate the filament entirely**: at 390px the wordmark measured **max lum 171 with nothing above 200 — darker than the flat fill it replaced**, i.e. a silent regression visible only on small screens. Caught by screenshotting at 390 as well as 1440 rather than trusting the desktop render. Fixed by expressing the stroke in **em** so it scales with the type (`0.0174em` == the 1px that worked at 3.6rem, ~0.6px at 2.2rem), which needed no media-query special case; mobile now measures max 223 / 7.5% ≥200 with visible cores. Variants measured at both widths by `.qwen/tmp/stroke-lab.py` (renders one header per pass so band detection is unambiguous, `1440` and `390`).

## 4. Decision log (rewrite-era)

New owner decisions for the rewrite are recorded here, numbered R1, R2, … The legacy decision log (its §8 #1–34) remains binding and is distilled as D1–D17 in PLAN.md §2 — do not re-litigate those. Stack-audit decisions below were taken with full discretion per the audit brief; none are product-visible or hard to reverse, so they are recorded rather than blocking.

- **R1 — Python 3.13 + uv.** Runtime on 3.13 (3.14 is current stable but only ~11 months out); uv for lockfile hygiene + build speed (`uv.lock` committed). Replaces M0's 3.11/pip.
- **R2 — Django 6.1 over staying on 5.2 LTS.** Current stable (6.1.1, 2026-09-02); zero migration cost on a fresh codebase, while 5.2's security EOL (2028-04) would force the same move within a year. New `MAILERS` setting adopted from day one.
- **R3 — uvicorn/ASGI replaces gunicorn/WSGI.** Django's forward path (async views, future WebSockets); no async views needed yet — sync code runs fine under ASGI.
- **R4 — Task queue deferred to M2, then Django-Q2 on Postgres.** M1 has zero background tasks; when the TMDB backfill lands (D11), Django-Q2 (MIT, active) with a Postgres cluster replaces celery + django-celery-beat + the redis broker in one package, its built-in scheduler covering periodic jobs. Rejected: Celery (inertia — 3 packages + Redis), ARQ (needs Redis), Dramatiq (LGPLv3+, heavier model), plain async views (no retry/survival for a ~15-min job).
